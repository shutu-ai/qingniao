# 青鸟(QingNiao)设计文档 — 去中心化远程控制(Windows)

日期:2026-11-11
状态:已评审,待用户批准(评审问题已归档:4 项用户拍板,4 项设计者定夺见 §14)
产出物:Windows 10/11 x64 远程控制软件(被控端服务 + 主控端应用 + 组网守护)

---

## 1. 意图与动机

用户当前使用网易 UU 远程,体验"顺滑如本地屏幕",但它依赖厂商外网服务器做设备撮合、
NAT 打洞与中继。目标:自研一个**不依赖任何厂商云**的 Windows 远程控制软件,在
"公网 NAT 节点 ↔ VPN 节点"混合拓扑下互连,不可直达时**自动经中间节点多跳中继**,
同时把 UU 的低延迟串流工程(采集→硬编→传输→硬解→注入)作为本项目学习的核心。

命名:**青鸟**——传信之鸟,取"中介传书"之意(用户已确认)。

## 2. 现实拓扑(已确认的事实)

```
 公网侧(节点都在 NAT 后,无任何公网入口)      VPN 侧(同一 VPN 内互通)
   A ──┐                                        ┌── C
   D ──┼── (首连靠邀请码/IPv6/打洞) ── B ────────┼── E
   … ──┘                                        └── …
```

- 公网侧节点(A 及未来几台):全部在 NAT 后,**没有**公网 IP、端口映射、VPS 可用
- VPN 侧节点(B、C 及未来几台):同一 VPN 内天然互通;B 是两个域之间的天然桥梁
- **公网侧节点策略上不允许加入该 VPN**(已与网管确认不可行)
- A↔B 今天的连通性来自 UU 远程服务器的撮合——撤掉 UU 后必须自建"介绍人"机制
- 规模:个位数到十几台;新节点会持续加入,公网/VPN 两侧都有

## 3. 目标

- **G1** Windows 10/11 x64 单平台(一期仅此平台)
- **G2** 去中心化组网:无厂商云、无必需中央服务器;新节点仅需一次性引导(邀请码/
  IPv6/同 VPN)即可入网,入网后由网内节点互相介绍认识新朋友
- **G3** 自动多跳中继:A 到 C 不可直达时自动经 B 转发;中继节点只见密文
- **G4** "顺滑如本地"的串流管线:零拷贝采集 → 硬件编码 → 抗弱网 UDP 传输
  (FEC + 自适应码率)→ 硬解 + 低延迟呈现 → 低延迟输入注入
- **G5** 无人值守:被控端开机自启(Windows 服务),主控端随时可连;**锁屏与
  UAC 安全桌面下仍可查看+操作**;重启后停在登录界面时不可连,有人登录一次后恢复
- **G6** 首连优先级:同 VPN 零配置 > mDNS 同网段 > IPv6 直连 > 邀请码打洞兜底
- **G7** 性能基线:LAN/VPN 内端到端 p95 延迟 < 60ms;公网(含中继两跳)< 150ms;
  帧率目标 60fps,弱网自适应降至 30fps;分辨率自适应(含 4K 屏)

## 4. 非目标(一期不做)

- 手机端 / TV 端 / macOS / Linux(用户明确"先只做 Windows")
- 会话录制、远程开机(WOL 可列为 P2)
- 做成通用 mesh VPN 产品(Yggdrasil 是内部件,不是交付物)
- 兼容 RDP/VNC 协议或接管 Windows 自带远程桌面会话(RDP 模式)

## 5. 反目标(出现即失败)

- 任何形式的厂商云依赖、遥测回传、在线激活
- 屏幕内容或键鼠事件明文过网
- 中继节点能解密转发内容(破坏端到端加密语义)
- 无鉴权接入:无人值守 ≠ 无凭据,未在信任列表的设备必须被显式批准

## 7. 架构总览

```
┌─────────────────────────────────────────────────────┐
│ 远控应用层(自研,项目灵魂)                          │
│  采集 → 编码 → 传输 → 解码呈现 → 输入注入 + 控制协议 │
├─────────────────────────────────────────────────────┤
│ Yggdrasil(现成,子进程)                             │
│  mesh 路由 / 多跳自动中继 / overlay 编址(每节点 IPv6)│
├─────────────────────────────────────────────────────┤
│ 链路管理器(自研,小)                                │
│  mDNS 发现 / IPv6 探测与直连 / STUN 分类 / 预约打洞  │
│  邀请码协议 / 成功链路注入 Yggdrasil                 │
├─────────────────────────────────────────────────────┤
│ 物理网络:现有 VPN · IPv6 · 公网 NAT                 │
└─────────────────────────────────────────────────────┘

进程模型(经典 Windows 远控架构,不可简化):
  青鸟服务(Windows Service, SESSION 0):组网守护 + 鉴权 + 会话调度
      ↕ 本地 IPC(命名管道/gRPC over localhost)
  会话助手(用户会话内进程):采集 + 输入注入(服务无法直接触碰交互桌面)
  主控端(UI 进程):发起连接、串流解码呈现
```

> **注意(关键约束)**:屏幕采集与 SendInput 必须运行在交互用户会话内,
> Windows Service(session 0)做不到。服务/助手拆分是硬性架构要求,不是优化。

**锁屏 / UAC 场景(用户已确认必须支持)**:会话被锁或 UAC 安全桌面激活时,
输入注入切换到服务侧 SYSTEM 注入通道(向 Winlogon/安全桌面发送输入),
采集切换到服务侧锁屏画面捕获。具体实现(UIAccess、SAS、桌面切换时机)是
builder 的首个技术 spike,RustDesk 证明该路径可行。登录界面(无会话)不做,
因此不需要配置 Windows 自动登录。

## 8. 串流管线(自研核心,builder 规划重点)

1. **采集**:首选 DXGI Desktop Duplication(无边框、GPU 零拷贝、全屏);
   Windows.Graphics.Capture 为备选(支持窗口级采集;Win10 上有黄色边框,
   仅 Win11 24H2+ 可关)。采集器输出 GPU 纹理,不做 CPU 回读。
2. **编码**:首选 Media Foundation 硬件 MFT(`MFT_ENUM_HARDWARE`)——它会透明
   选到 NVENC/QSV/AMF;仅当实测不足时才直连厂商 API。低延迟配置:无 B 帧、
   短 GOP 或 intra-refresh、CBR、ultra-low-latency tuning。
3. **传输(分期策略)**:
   - M2(MVP):全走 QUIC(`System.Net.Quic`,.NET 8 内置,基于 msquic),
     视频每帧独立 stream 规避队头阻塞——先用可靠通道拿到端到端可用
   - M4(打磨):视频路径换自研 UDP(帧分片 + FEC(XOR 或 RS)+ NACK 重传 +
     丢包/延迟联合的 AIMD 拥塞控制 + pacer);控制/输入通道保留 QUIC
   - MTU:Yggdrasil overlay 有自己的 MTU(数值 builder 需实测确认),VPN 又叠加
     开销;传输层必须做 PMTUD,分片大小可配置
4. **解码呈现**:DXVA/D3D11VA 硬解 → D3D11 低延迟呈现(waitable swap chain、
   不入垂直同步队列);DPI awareness = per-monitor v2。
5. **输入注入**:SendInput(鼠标绝对坐标按目标显示器映射、滚轮、扫描码键盘、
   Unicode 文本注入);输入事件走独立低延迟通道,不等视频回路。
6. **自适应**:发送端按拥塞控制输出调整目标码率(1–20 Mbps)与帧率;
   分辨率降级为最后手段。

## 9. 安全(设计决定,builder 只选库)

- **身份**:每节点长期 Ed25519 密钥;节点 ID = 公钥指纹;展示名 = 主机名 + ID 前 8 位
- **端到端加密**:会话必须以双方长期身份密钥做相互认证(Noise_XX 或 TLS 1.3
  mutual),会话密钥前向保密。**不依赖** Yggdrasil 的链路加密——中继节点必须
  只见密文。库选型留给 builder
- **访问控制**:被控端维护"信任设备列表"。信任建立的三条途径(用户已确认
  "邀请码即凭证"语义,无人值守首连可行):
  1. **信任码**:被控端预生成,持有者入网即自动加入信任列表;可设过期、
     可吊销、含 nonce 防重放——无人值守场景的标准路径
  2. **现场 TOFU**:首连时被控端弹窗人工确认(补充路径)
  3. **入网码**:只建立 mesh 可达性、不通屏,不建立会话信任
  可配置为"每次连接弹窗二次确认"
- 无遥测;日志仅本地,不含屏幕内容

## 10. 组网与首连协议

- **发现优先级**(每条成功即注入 Yggdrasil,多链路并存、按代价选路):
  1. 同 VPN:配置 VPN CIDR → 直接连 VPN 内网地址(零配置入网)
  2. mDNS:同链路层网段自动发现(服务名 `_qingniao._udp`)
  3. IPv4 打洞(**公网侧关键路径——用户已确认公网侧家宽无 IPv6**):
     公共 STUN 服务做映射地址发现 + NAT 类型分类(RFC 5780 风格,多 STUN
     交叉探测);对称 NAT 检出后明确警告"此链路可能打不通"并给出补救选项;
     预约式打洞:邀请码载荷 = {长期公钥, STUN 映射地址集, 时间窗, nonce},
     双方窗口内同步互发;对端口可预测的 NAT 附加端口预测尝试
  4. IPv6 直连:降级为机会性检查(M0 仍检测;当前已知两侧都没有,未来宽带
     变化时自动受益,无需改设计)
- **打洞失败的诚实出路**(物理限制,写入产品文案):双侧对称 NAT 时,唯一
  出路是任一侧获得公网入口(端口映射/任何 VPS)或更换网络;软件无法绕过。
  入口出现时,该节点自动升级为常驻 peering 枢纽
- **邀请码**:发起方生成,base64,5 分钟有效;对方粘贴导入;成功即完成首连+TOFU
- **入网后**:节点间经 Yggdrasil overlay gossip 同步在线表,新节点由网内成员
  介绍,不再需要任何外部信道
- **链路注入 Yggdrasil 的方式是已知风险点**:优先尝试 admin socket 动态
  addPeer;若 Yggdrasil 不接受指向已打洞 socket 的 peer,备选方案 = 链路管理器
  在本机做 UDP 桥(127.0.0.1 转发到 yggdrasil listener)。builder 验证后定夺
- **自检工具 M0 必须先交付**:检测并报告 IPv6 可用性、NAT 类型、GPU 编码器、
  VPN 网段——IPv6 若普遍可用,整个打洞子系统降级为兜底

## 11. 里程碑(供 writing-plans 细化)

| 阶段 | 内容 | 验收 |
|------|------|------|
| M0 | 环境自检 CLI(小工具,最先做) | 一页报告:IPv6/NAT 类型/编码器/VPN 网段 |
| M1 | Yggdrasil 托管 + VPN/mDNS/IPv6 链路 | VPN 侧三节点互 ping overlay 地址 |
| M2 | 串流 MVP(QUIC 版):服务/助手拆分、单屏查看+控制 | LAN 内可流畅操作,测得延迟数据 |
| M3 | IPv4 打洞(关键路径)+ 两档邀请码 + 锁屏/UAC 注入通道 | A(公网)→ B(NAT)→ C(VPN)全链路可达;锁屏下可操作 |
| M4 | 自研 UDP+FEC 视频路径、自适应码率、多显示器;P1 功能 | 公网两跳 p95 < 150ms,弱网不冻结 |

**已知风险**(按杀伤力排序):
1. 双侧对称 NAT(CGNAT)打洞必败——已确认为关键路径(公网侧无 IPv6):
   M0 尽早测 NAT 类型,失败时给出补救文案;真机随时可用于验收(已确认),
   可选择性搭建 NAT 仿真测试台复现边界 NAT 类型(builder 自行决定,非必选)
2. Yggdrasil 动态注入链路的可行性未验证——M1 内首个 spike
3. .NET 的 ICE/STUN 生态弱于 Go(pion)——链路管理器可能需要自写简化版,
   或评估孤立组件用 Go 写一个 ~几 MB 的守护进程(违背单语言决策,除非实测
   .NET 无法覆盖,若如此需回报用户重新决策)
4. MF 硬编在某些 GPU/驱动组合下退化——M0 的编码器探测兜底

## 14. 设计者定夺记录(通读时可否决)

1. **.NET 8 → .NET 10 LTS**:用户确认的"C#/.NET 8"中,版本部分由设计者改为
   .NET 10——.NET 8 LTS 支持已于 2026-11-10 到期,面向公网的新工具不应构建在
   已停安全更新的运行时上;语言与 API 形态不变,System.Net.Quic 仍在
2. **多 peer 冗余**:B 是单桥,设计上鼓励每个节点与 ≥2 成员建 peering
   (Yggdrasil 多链路天然支持);M0 增加上行带宽测量
3. **VPN 内部形态不问人**:MTU/UDP 双向/出站可达性由 M0 自检工具实测,
   不依赖用户去询问网管协议名
4. **VPN 侧机器常驻服务许可**:默认可行——UU 远程已在这些机器上常驻同级组件;
   若那些机器另有管控策略,需用户纠正此假设
